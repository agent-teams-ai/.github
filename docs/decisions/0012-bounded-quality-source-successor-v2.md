## Decision and bounded ownership

and the installation evidence. The caller is generated by
`callerWorkflowDefinition(S)` from the immutable source and checked by its
`assertCallerWorkflow`; `S` is
`d2904ef5181b1a3f42da2b6fad7e5f7fccad1ecd`.
It calls only the exact source workflow at that SHA through
`pull_request_target`, with the canonical permissions, no inputs and no
secrets. Source execution remains owned by the immutable protected branch
`governance/quality-source-successor-v2`, locked by ruleset `25469495`.

The source admits PR369 only through its exact finite before/after tuple.
Its ordinary and dependency routes continue to execute the real frozen v1
verifier. Complete paginated file metadata, rehashed complete Git trees,
regular-file modes, actual base install bytes and live event/source binding
remain required. This installs no generic controller route, broad quality-file
exemption, dependency upgrade or replacement verifier.

All five frozen v1 inputs and the four quality-process/test-runner inputs
remain unchanged. After installation, these three installation files are also
byte-immutable under the v2 route. Future canary results belong in PR comments
or separately reviewed ordinary evidence; they must not be appended to these
frozen installation files. Changing this contract requires an explicitly
reviewed successor rather than a self-approved caller or evidence edit.

## Installation and permanent cutover sequence

The main caller does not yet exist on the installation base. The earlier
successful source push targets PR369 and cannot certify a new installation
PR. Install through the unchanged v1 ordinary gate: re-add the old
`docs-source-successor-v1` requirement before removing the temporary new
`docs-quality-source-successor-v2` requirement. Read back the complete owner
rulesets at both steps. Require genuine old-v1 and all unrelated native checks
on the exact installation head, then perform the normal owner-guarded merge.
No required context is forged, bypassed or treated as passing by this ADR.

After that merge, run genuine installed-main caller canaries: an ordinary
positive PR and a protected-input negative PR. Bind each result to its actual
PR/base/head, defining immutable source, run/attempt, decisive jobs and status.
Do not merge the negative canary. A failure while the new context is optional
proves rejection, not merge blocking. After both canaries complete, inspect
fresh owner-full source, main and identity protections, then add the new source
requirement while retaining the old one. On the same negative head, confirm
that the failed v2 context is required and mergeability is blocked, without a
red merge attempt or auto-merge. Only after that proof and the positive result
may the old requirement be removed permanently. Preserve the other four main
checks, separate identity check, App identities, strictness, PR protections and
every unrelated ruleset field throughout.

The permanent installed-main caller, positive and negative canaries, and final
permanent cutover remain pending at this installation snapshot. Source
qualification and PR369 merge do not establish those later results.

## Compatibility, migration and rollback

This is a Central development-governance installation. It changes no consumer
admission, Cohort, package, lockfile, product contract, production runtime or
published architecture standard. The existing quality route and full
`pnpm check` remain required; local installer proof is not hosted qualification.

If installation fails or a canary misses its expected outcome, stop before
permanent cutover and retain the old source requirement. If a later
installed-main failure requires a return to v1, add the old requirement before
removing the new one, with fresh
owner-full readback and all unrelated protections preserved. Do not rewrite
the locked source, frozen installation or historical inputs to obtain green
checks. Any file removal or replacement follows a separately reviewed
successor/rollback route and normal merge, without bypass.
